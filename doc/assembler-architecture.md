# Архитектура ассемблера `rasm`

Документ описывает текущую реализацию ассемблера (`src/RiscA.Core/Asm` + CLI
`src/RiscA.Assembler`) и детальный план вехи **A1** — расширений, без которых невозможен
компилятор C (см. `doc/compiler-architecture.md`, раздел 5). Ссылки: спецификация ISA —
`doc/RiscA.MD`; подробный справочник кодировок с примерами — `doc/instruction-set.md`;
эмулятор и формат симовлов — `doc/emulator-architecture.md`.

## 1. Назначение и границы

`rasm` принимает **один** исходный файл `.rasm` (подключаемые фрагменты — через `.include`)
и выдаёт плоский бинарный образ: последовательность 16-битных слов, начинающаяся с адреса 0.

Что осознанно **не** делает (границы модели):

- нет объектных файлов и линкера — вся программа (код, данные, библиотеки) собирается за
  один проход из одного дерева исходников. Компилятор C следует той же модели: `rcc`
  выдаёт один `.rasm` на всю программу с «вшитой» libc (`compiler-architecture.md`, раздел 1);
- нет директивы адреса (`-a <addr>`): образ всегда стартует с 0; все переходы
  относительные, поэтому образ переезжает на `0x0001_0000` (точка сброса эмулятора) без
  пересборки, лишь бы сохранялось выравнивание;
- нет макросов и условной сборки — до тех пор, пока их не потребует компилятор;
- выражения только над числами, не над метками (`dw label + 4` — нельзя, `dw label` — да).

## 2. Модули и данные

| Файл | Содержимое |
|---|---|
| `Asm/Preprocessor.cs` | `Preprocessor` — распознавание `.equ`/`.include` тем же движком правил (полные грамматики директив), склейка `.include`, сбор `.equ`-констант; `.func` здесь не обрабатывается |
| `Asm/Rule.cs` | `RuleHandler<TCtx>` — общий делегат обработчика правила (им пользуются и парсер, и препроцессор) |
| `Asm/Token.cs` | `TK` (виды токенов), `Token`, `Tokenizer.TokenizeLine`, `IsReserved` |
| `Asm/Parser.cs` | `ParsedInstruction`, `Parser` — набор правил и обработчиков + `ProcessToken` (движок) |
| `Asm/Assembler.cs` | `SrcLine`, `Assembler` — адресация, метки, разрешение ссылок |
| `ISA/Instruction.cs` | `Instruction` (readonly struct над `ushort`), enum'ы полей, `CheckImmLimits`, `SetImm`, `CalcRef`, `ToString` |
| `Verbose.cs` | флаги `-vp` / `-vi` |
| `RiscA.Assembler/Program.cs` | CLI: `-i` вход, `-o` бинарник, `-l` листинг, `-v[-vp -vi]`, `-V`; печать листинга |

Ключевые структуры:

- **`Token`** — `(TK тип, строка, позиция, intValue, strValue)`. Токенизатор регистронезависим
  для мнемоник и регистров (`r0..r15` несут номер в `intValue`); числа: десятичные, `0x`, `0b`;
  строки — в одинарных и двойных кавычках (обе дают `STRING`, данные `db` по-прежнему только
  в одинарных); комментарий `;` съедает остаток строки; в конце дописывается `EOL`.
   Слово вида `.имя` читается как отдельный токен: известные слова получают свои
   виды: `EQU`/`INCLUDE` (их разбирает препроцессор) и `FUNC` (его разбирает парсер),
   любая прочая — `DOTNAME` (ошибочное имя препроцессор печатает сам, токен сохраняет
   написание как в исходнике). `IsReserved` — проверка, что слово не
   может быть меткой/константой (это мнемоника или регистр).
- **`SrcLine`** — строка исходника + номер строки + файл + адрес + `ParsedInstruction`
  (для строк директив препроцессора, не генерирующих код, `ParsedInstruction` предзаполнен
  пустым — так `.equ`/`.include` не парсятся). `.func` — не директива препроцессора: строка
  проходит как обычный код, её парсит парсер, а правило `ParseFuncDirective` помечает
  `ParsedInstruction.IsFunc` — по этой метке ассемблер вставляет перед входом функции
  выравнивающий `NOP` и строит границы пулов (6.3).
- **`ParsedInstruction`** — результат разбора **одной строки**: `List<Instruction>` halfword'ов
  (одна строка может дать несколько: `db 'text'`, `dw label` — два halfword'а, разворот `li` —
  до четырёх), плюс `Label`, **`Fixups: List<Fixup>`** (отложенные ссылки на метки, 6.2),
  `PoolRequests`, `InlineSlot` (строка уже несёт инлайн-мини-пул, 6.1), `IsFunc`, `IsDW`,
  `IsDB`, `IsPool` (служебный слот пула, вставленный ассемблером).
  Инвариант модели: адрес строки + 2×индекс halfword'а = адрес инструкции.
- **`Fixup`** — изменяемый класс отложенной ссылки: слот halfword'а, имя метки, `FixupKind`
  (Branch/Call/Jr/PoolRef/DataAddr), `Target` (слот пула для PoolRef) и `Reg` (регистр
  разворота `j`) — подробности в 6.2.
- **`Instruction`** — immutable struct: набор кортежей `(mask, shift)`, геттеры
  (`OpCode, Rd, Rs, Func1, Func2, Func21, Func22, Func4, Imm3, Imm7, Imm7s, Imm8, Imm8s, Imm9, ImmCallJr`),
  билдеры `with*` (`this`-копии), `CheckImmLimits(imm)` (диапазоны по опкоду; отдельно
  `SHL/SHR: 0..15`, чтобы ассемблер не давал тихого `imm & 0xF`), `SetImm` (универсальная
  запись imm в нужные поля, для CALL/JR — 11-битное splitting по `Imm7|Rd`),
  `CalcRef(addr)` — куда указывает готовая инструкция (BRANCH/LDI: шаг инструкция ×2 байта;
  CALL_IMM: шаг **слово** ×4 от слова инструкции; JR: шаг инструкция).
  `ToString` — человекочитаемая расшифровка для листинга/дизассемблирования.

## 3. Конвейер

```
файл.rasm
  └─ Preprocessor.Process:
       каждая строка токенизируется и прогоняется через тот же движок правил, что и парсер
       (своё дерево правил: сначала правила-выражения над числами, затем полные грамматики
       EQU и INCLUDE, затем одно правило-репортнер для EQU/INCLUDE/DOTNAME → «preprocessor:
       токен не принят, файл/строка/токен»); строка является директивой,
       только если её грамматика свела стек токенов в ноль целиком, иначе это обычный код —
       в том числе строка `.func`, которую целиком забирает парсер (правило ParseFuncDirective);
       склейка .include (каждый файл один раз, поиск: каталог включаемого → каталог корня → cwd,
       циклы игнорируются)                     .equ-константы собираются вторым проходом
  └─ Pass A (Parser.ParseLine на каждой строке):
       подстановка констант (LITERAL → NUMBER; «констанка как метка» — ошибка)
       движок правил: список (шаблон токенов → обработчик), цикл «найти первое вхождение
       шаблона в стек токенов — схлопнуть»; выражения (−N, скобки, +−*/) схлопаются в NUMBER;
       «метка:» в начале строки уходит в ParsedInstruction.Label;
       псевдокоманды li/la/j разворачиваются обработчиками правил (6.1), ссылки переходов
       на метки — в Fixups без проверки дальности (её делает петля 6.4);
       .func — правило ParseFuncDirective помечает строку (IsFunc), ассемблер
       вставляет перед входом NOP для 4-байтного выравнивания на границе;
       непустой остаток токенов = ошибка синтаксиса
  └─ Pass B+C (Assembler, цикл до неподвижной точки, не более 10 раундов — 6.4):
       пересчёт адресов всех строк (curAddress += 2 × число halfword'ов, метки в labelMap)
       → разрешение и релаксация всех Fixups: dw label → абсолютный адрес в 2 halfword'а,
       offset в единицах инструкции (ветки, LDI, JR) или слова (CALL_IMM, с проверкой
       4-выравнивания цели), CheckImmLimits, SetImm; недостижимые ссылки — разворот
       (инверсия ветки + JR, LDI+JMP/CALL r7 через пул или инлайн-мини-пул, слоты пулов,
       AlignFuncs); замены только удлиняют код — петля монотонна и сходится
  └─ Program.cs: .bin (raw halfword'ы LE), .lst, листинг -vi с CalcRef-аннотациями
```

Прямые пользовательские правила описаны в `doc/README.md` (раздел «Директивы ассемблера»).

## 5. Ограничения до A1 — почему она была нужна (историческая справка)

1. **`RefLabel` одна на строку.** Псевдокоманда вида `la` разворачивается в две связанные
   записи (LDI + слот пула), а `j label` — в один halfword с отложенной проверкой дальности.
   Одна ссылка не покрывает ни разворот, ни пул.
2. **Нет релаксации.** Дальность ветки ±128 инструкций, CALL ±1024 слова — для кодогена
   компилятора это норма жизни (циклы, большие функции). Сейчас «далеко» = ошибка.
3. **Нет `li`/`la`/`j`.** Бэкенд компилятора вынужден сам эмитить `movi/movl`-цепочки и
   вручную расставлять пулы — знания про кодировки утекают из бэкенда в код, чего быть не
   должно (см. «зачем A1» в `compiler-architecture.md`, раздел 5).
4. **Проход разрешения ссылок единственный.** Как только разворот меняет длину кода,
   адреса съезжают — нужен цикл до неподвижной точки.

## 6. Веха A1 — план и реализация (детально)

Раздел описывает A1 так, как она реализована в `src/RiscA.Core/Asm/` (`Fixup.cs`,
`Parser.cs`, `Assembler.cs`); расхождения плана с кодом исправлены по факту кода.

Общий принцип: **все знания о кодировках прячутся в `rasm`**; бэкенд `rcc` пишет наивный код
с псевдокомандами, ассемблер сам разворачивает, раскладывает по пулам и релаксует.

### 6.1. Псевдокоманды

Псевдокоманды **не имеют своей кодировки**: парсер разворачивает строку в 1…4 настоящих
инструкции. Смысл — чтобы и кодоген (`rcc`), и человек писали код, не зная про кодировки:
ширину констант, цепочки `MOVI`/`MOVL`, расположение пулов, дальность переходов. Новые
токены `TK.LI/LA/J/PUSH/POP` добавляются в `Tokenizer` (в словарь мнемоник; `IsReserved`
подхватит их автоматически), разворот — обработчиками в `Parser`: они добавляют несколько
halfword'ов в `ParsedInstruction.Instructions` и записи в `Fixups`.

#### `li Rd, c` — загрузка произвольной константы

Аппаратной инструкции «загрузить 32-битное число в регистр» в RiscA нет: есть только
`MOVI Rd, imm` (записывает 0..255) и `MOVL Rd, imm` (дописывает байт: `Rd = (Rd<<8)|imm`).
`li` собирает из них минимальную цепочку: число берётся как 32-битный паттерн, старшие
нулевые байты пропускаются, первый ненулевой байт грузит `MOVI`, остальные — `MOVL`
(у самого `MOVI` мнемоника та же, что у настоящей инструкции, — разворота в таблицу кодов
не нужно):

```
li r1, 0x12345678   →  movi r1,0x12 ; movl r1,0x34 ; movl r1,0x56 ; movl r1,0x78   (4 инстр.)
li r2, 5            →  movi r2, 5                                                  (1 инстр.)
li r3, 0            →  movi r3, 0          ; особая граница: хотя бы один байт грузим всегда
li r4, -1           →  movi r4,0xFF ; movl r4,0xFF ; movl r4,0xFF ; movl r4,0xFF   (двухкомплементный паттерн)
```

Портит только `Rd`. Конфликт с `ADD Rd,imm` (0..127) и т.п. не возникает — `li` это
всегда ровно `MOVI`+`MOVL`, а не «самая дешёвая последовательность вообще» (короче может
быть через `shl`, но это задача peephole-оптимизации бэкенда, не ассемблера).

#### `la Rd, label` — загрузка адреса метки

Загружает в `Rd` **финальный адрес** метки (функции, строки, таблицы) — тот, который будет
после сборки всего образа. Первый выбор — `LDI Rd, [imm9]` читает 32-битный слот `dw метка`
из пула констант функции, но пул автору расставлять **не надо** — ассемблер сам создаёт
слот (раздел 6.3), сам считает `imm9` и сам пересчитывает его при релаксации. Если слот
пула окажется недостижим (LDI живёт в ±256 инструкциях), `la` не деградирует в `li`, а
переходит на **инлайн-мини-пул**: слот `dw` ставится прямо за загрузкой, а поверх данных
перепрыгивает безусловный переход:

```
la r1, msg          →  ldi r1, +2     ; LDI читает слово через 2 инстр. от себя
                       jr  +3         ; от позиции jr перепрыгнуть 2 halfword'а данных
                       dw  msg        ; финальный адрес метки — всегда «под рукой»
```

(`jr +3` — точное значение считается из положения `jr`, это внутренняя развёртка
ассемблера, вручную такую команду писать не нужно.) `dw` обязан быть word-выровнен — если
строка стоит на нечётном halfword-индексе, ассемблер вставляет `nop` перед `dw`
(см. выравнивающий `NOP` у `.func`), величины `imm` при этом сдвигаются на 1.

Три причины, почему это лучше отката к `li Rd, <адрес>` (цепочка movi/movl та же по цене
3–4 halfword'а):

1. **Достижимость гарантирована**: слот в 2–3 инструкциях от LDI, диапазон больше никогда
   не проверяется и не может «уехать» при релаксации соседей.
2. **Не портится временный регистр** (ср. `j` через регистр, который портит `r7`).
3. Главная, на вырост: **абсолютный адрес остаётся в записи `dw`, а не в кодировке
   инструкции**. `li` зацементирует адрес в цепочке `movi`/`movl` — в готовом образе такую
   ссылку не найти. При инлайн-пуле каждая ссылка на абсолютный адрес — это `DataAddr`
   фиксип, а весь набор `dw` в образе — готовая **таблица релокации**: загрузка образа по
   произвольному адресу (будущее `-a`, A2) сведётся к пересчёту слов из этого списка.

`la Rd, <число>` тоже разрешена — это синоним `li` (единообразие для кодогена: бэкенд может
всегда печатать `la`, а разницу ассемблер спрячет). Портит только `Rd`.

#### `j label [, rN]` — безусловный переход без ограничений по дальности

Переход на метку. Первый выбор ассемблера — `JR` (1 halfword, но ±1024 инструкции); если
не дотягивает — `LDI rN, [@pool]` + `JMP rN` (адрес из пула, дальность не ограничена).
Временный `rN` по умолчанию `r7`; явная форма `j label, r3` использует `r3`. Форма `JR`
ничего не портит, пуловая форма портит `rN`. Это главная псевдокоманда для кодогена:
компилятор печатает `j` и не считает дальность ветки.

#### `push rN` / `pop rN` — макрос стека из спеки

`doc/RiscA.MD` в разделе ABI задаёт стек не инструкцией, а макросом из двух настоящих
команд (`SUB R15, 4` + `STW [R15+0], Rd` и обратно). Псевдокоманда печатает этот макрос
именно так, слово в слово, — своей кодировки у неё нет и в эмуляторе она не появляется:

```
push r3   →   sub r15, 4        ; слот появляется до записи
              stw [r15+0], r3
pop r4    →   ldw r4, [r15+0]   ; сначала чтение, только потом ADD
              add r15, 4
```

Порядок команд — не на выбор: `push` двигает `R15` до записи (стек растёт вниз, слот
появляется перед заполнением), `pop` читает до `ADD` — из-за этого пара `push`/`pop`
возвращает `R15` ровно туда, где он был. Цена — ровно 2 halfword'а на команду, то есть
пара всегда занимает целое число слов и не сдвигает выравнивание кода после себя
(`NOP`-выравнивание `.func` от неё не зависит).

Портит только `R15` (законно: это и есть стек ABI) и читает/пишет `rN`. `push r15` /
`pop r15` — ошибка сборки: сдвинуть указатель и тут же записать его по новому месту
значения никто не хочет, а `pop r15` ещё и вернул бы старое значение указателя, потеряв
кадр. В именованной области A2 `push`/`pop` попадают под тот же запрет, что и ручная
правка `R15` (7.2, 7.7), и причина не в абстрактном «кадре пролога»: выходов у области
сколько угодно (7.3), поэтому `ret` законно стоит между `push` и `pop`, а эпилог считает,
что к нему пришли с `R15` ровно там, где его оставил пролог, — несбалансированный по пути
на выход `push` тихо сдвинул бы весь кадр. В области без имён кадра нет, и `push`/`pop` —
обычный способ работать со стеком.

#### Почему не добавляем `mv`

В ARM/RISC-V `mv` — это алиас, компенсирующий особенности их `mov` (ограничения операндов,
псевдо-натура). В RiscA `MOV Rd, Rs` — полноценная настоящая инструкция opcode 0 без
ограничений, так что алиас `mv` был бы чистой избыточностью: везде, где хочется `mv`,
пишем `mov` (кодоген `rcc` — тоже). Правило-алиас в парсер не добавляем; если когда-нибудь
понадобится (например, `mv` как «mov с альтернативным разбором» — вряд ли), решение
пересматривается явно.

`db`/`dw` с числами, строками и метками уже есть — данные бэкенд умеет выдавать сегодня.

### 6.2. Фиксипы вместо `RefLabel`

```csharp
enum FixupKind { Branch, Call, Jr, PoolRef, DataAddr }
// Slot — индекс halfword'а внутри ParsedInstruction.Instructions
class Fixup { int Slot; string Label; FixupKind Kind;
              SrcLine? Target;   // слот пула, на который указывает PoolRef (null у
                                 // рукописного ldi — он грузит содержимое по метке)
              int Reg = 7; }     // целевой регистр разворота j label, rN
// ParsedInstruction.Fixups: List<Fixup>;  RefLabel удалён, IsDW/IsDB/IsPool на месте
```

`Fixup` — изменяемый класс, не record: при развороте строки `InsertAndShift` сдвигает
`Slot` всех фиксапов строки, вставленных после точки вставки; релаксация меняет `Kind`
(`Jr → PoolRef`) и `Label` (у инвертированной ветки — на скрытую `@over<n>`).

| Kind | Поле | Единицы | Диапазон | Особенности |
|---|---|---|---|---|
| `Branch` | `Imm8` ветки | инструкции | −128..+127 | при выходе — релаксация 6.3 |
| `Jr` | `Imm7\|Rd` | инструкции | −1024..+1023 | при выходе — `LDI`+`JMP` |
| `Call` | `Imm7\|Rd` | **слова** | −1024..+1023 | цель 4-выровнена (проверка как сейчас); при выходе — `la r7` + `CALL r7` |
| `PoolRef` | `Imm9` LDI | инструкции | −256..+255 | разрешение после расстановки пулов; при выходе — инлайн-мини-пул (6.1) |
| `DataAddr` | 2 halfword'а | абсолют | — | как нынешний `dw label` |

### 6.3. Пулы констант

- Строка, запросившая пул (`la` или релаксированный `j`/`call`), помечает
  `ParsedInstruction.PoolRequests: List<string>`.
- `Assembler.GetPool` на первый запрос вставляет **слот пула** — служебный `SrcLine`
  с `dw`-записью (два halfword'а с `DataAddr`-фиксипом), помеченный `IsPool`, без метки
  (в листинге виден по псевдоисходнику `dw <label> ;pool`). Слот ищется/кэшируется по ключу
  `(область, метка)`: область — ближайшая `.func` выше строки, либо `null` для файла без
  `.func`; вставляется в конец области (перед следующим `.func` или концом файла).
  При нечётной позиции слота перед `dw` вставляется `NOP` — адрес абсолютного слова
  всегда word-выровнен (его читает и `LDI`/`LDW`, и будущий загрузчик-релокатор).
  Если развороты сдвинули `.func` с 4-выравнивания, `AlignFuncs` возвращает `NOP`
  на границу — только добавляет, никогда не убирает.
- `PoolRef` фиксируется на конкретный слот пула (`Fixup.Target`), адрес слота пересчитывается
  на каждой итерации релаксации. Если расстояние больше ±255/256 инструкций — `la` переходит
  на инлайн-мини-пул (6.1). Слот пула при этом **остаётся** (безобидная мёртвая запись,
  следующий `la` на ту же метку в той же области попадёт в тот же слот). Обратно в пул
  решение не откатывается: переключение «пул ⇄ инлайн» туда-сюда ломало бы монотонность
  роста кода и петля могла бы зациклиться.
- Пулы областей не сливаются между собой: локальность пула = предсказуемая близость к коду.

### 6.4. Петля релаксации

**Зачем это нужно.** У всех переходов RiscA фиксированная кодировка и конечная дальность:
`BEQZ/BNEZ` — ±128 инструкций от текущей, `LDI` — ±256, `CALL`/`JR` — ±1024. В коде руки
такое иногда можно облагородить вручную, но для кодогена компилятора «дальние» переходы —
норма: тело цикла в 200 инструкций уже за пределами ветки, а две функции на 300 инструкций
— за пределами CALL. Возникает парадокс: **настоящие расстояния между метками известны
только после всех разворотов, а сами развороты меняют длины и сдвигают адреса**. Релаксация
одной ветки добавляет 1–2 инструкции — и соседняя ветка, которая вчера доставала на +126,
сегодня не дотягивается. Поэтому одиночный проход разрешения ссылок (прежний Pass C)
превращается в цикл до неподвижной точки.

**Как работает цикл.** Инвариант каждой итерации: адреса всех `SrcLine` пересчитаны под
текущий список инструкций, и каждый фиксап либо входит в диапазон своего кодирования, либо
получает замену на более длинную форму. Ключевое свойство: замены **только удлиняют** код
(ветка 1→2+ halfword'а, `call` 1→2+ плюс слот пула, `j` 1→2+ плюс слот пула), а «дальних»
ссылок конечное число — значит процесс монотонно движется к разрешению и обязан
остановиться. Обычно хватает 2–3 итераций; потолок 10 — страховка от зацикливания при баге,
при его превышении — ошибка с перечислением проблемных меток.

```
изменено = true; итераций = 0
пока изменено:
    итераций++; если > 10 — ошибка «relaxation did not converge» + список проблемных меток
    пересчёт адресов всех SrcLine (Pass B-логика заново)
    для каждого фиксапа: вычислить offset/адрес цели
        Branch вне диапазона → заменить строку: <обратная ветка> over; j label; over:
            (beqz→bnez, bnez→beqz; «j» сам тоже может быть релаксирован следующей итерацией)
        Jr вне диапазона     → LDI rN,[пул]; JMP rN
        Call вне диапазона   → la r7, label; CALL r7
        PoolRef вне ±256     → la-строку заменить на инлайн-мини-пул: ldi+jr[+nop]+dw (6.1)
    изменено = (были замены/вставки удалений)
после сходимости — финальный пересчёт и запись фиксипов
```

**Правила с примерами.**

*Дальняя ветка* — инверсия условия плюс безусловный `j` (сам по себе `j` остаётся дешёвым
`JR`, пока цели не дальше ±1024):

```
        beqz r1, end        →   bnez r1, over   ; условие перевёрнуто: «не ветка» — прыгаем вниз
        ...                                       ; над дальним переходом
                                 j   end          ; JR, теперь диапазон ±1024 инстр.
        ...                                  over:
   end:
```

Эта конструкция хрупкая намеренно: вставленные `bnez over` и `j` сами могут оказаться
дальними (соседние развороты сдвинули `over:`) — их подхватит следующая итерация. Именно
поэтому нужен цикл, а не однократная подстановка.

*Дальний `j`/`JR` (за ±1024 инструкции)* — прыжок через регистр с адресом из пула:

```
        j   far              →   ldi r7, [@pool.k]   ; из пула функции — финальный адрес far
                               jmp  r7               ; дальность не ограничена
```

*Дальний `CALL` (за ±1024 слова)* — та же идея, форма `CALL Rd` без ограничений:

```
        call far             →   la  r7, far          ; ленивая форма: ассемблер сам решит,
                               call r7                ; пул это или инлайн-мини-пул
```

*Недостижимый слот пула (`PoolRef` вне ±256 инструкций для `LDI`)* — `la` переводится на
инлайн-мини-пул (`ldi` на слот в 2–3 инструкциях, `jr` поверх данных, `dw label` на месте) —
пример в 6.1. Дальность становится нерелевантной, слово адреса остаётся в `dw` (готовая
таблица релокации для `-a` в будущем).

**Пример сходимости** (цикл, из которого три ветки «на выход» разбросаны по 300
инструкциям кода):

```
итерация 1: дальняя ветка на loop_exit (смещение 260) → инверсия + j (JR±1024 хватает)
итерация 2: адреса сдвинулись на 2 инстр.; вторая ветка (была 126, стала 128) → та же замена
итерация 3: третью ветку сдвинуло на +4 до 131 → замена; j из итерации 1 всё ещё JR — ок
итерация 4: изменений нет — запись фиксипов, готово
```

**Временный регистр `r7`**: по умолчанию псевдо `j` и релаксации `call` портят `r7`. Для
человеческого кода это задокументировано (в `lib/uart.rasm` r7 — уже scratch), компилятор
управляет сам: у ABI аргументы в `r0..r5`, callee-saved `r8..r13`, значит `r7` для бэкенда
всегда свободен; при явном `j label, rN` ответственность на авторе строки.

`push`/`pop` из этого правила выпадают: скретча у них нет вовсе, а портят они `R15`, то
есть регистр, портить который разрешено по ABI. Фиксипов у них тоже нет — разворот
полностью известен в парсере, поэтому петля релаксации (6.3) их не трогает и длина строки
от релаксации не зависит.

## 7. Веха A2 — переменные, кадры и регаллок (принятый план, пока не реализовано)

Раздел 6 спрятал от кодогена всё, что он знал про кодировки. Но этого мало: `rcc` читает
QBE IL **до** того, как QBE сам раздаст значения физическим регистрам, — то есть до `rcc`
доходят виртуальные temporaries (`%t1, %t2, …`), а их в функции заведомо больше, чем 16
регистров у RiscA. Регаллок обязан быть где-то, и выбор — **в `rasm`**. Причины те же, что
у A1: бэкенд не должен знать про железку ни кодировок, ни количества регистров. Плюс
бонус: IL одноразовая (SSA — у временной переменной ровно одно определение), поэтому
живучесть в ассемблере считается тривиально, а `rcc` остаётся почти транспитератором IL.
Строка «базовый регаллок» переезжает из M3.2 в эту веху.

Одна и та же функция — как её пишут сегодня и как она будет писаться после A2
(`(a+b)*(a-b)`, значение `a` нужно дважды, поэтому без промежуточного регистра не обойтись):

```
.func mulsum:                   ; a→r0, b→r1 (ABI); результат обязан лежать в r0
    mov r8, r0                  ; второй операнд менять нельзя (он нужен снова),
    add r0, r1                  ;   значит заводят скретч: какой регистр и не испортит
    sub r8, r1                  ;   ли он кого-нибудь живого — это забота автора
    mul r0, r8
    ret                         ; ret тоже пишет автор
```

```
.func mulsum(a, b)
    mov t1, a                   ; имена ничего не знают: в какой регистр их положить
    add t1, b                   ;   и какой из этих mov убрать, решает rasm (7.6)
    mov t2, a
    sub t2, b
    mul t1, t2
    ret t1                      ; ret кладёт t1 в r0 и уходит к эпилогу; таких выходов может
.end                            ;   быть сколько угодно — эпилог на область один (7.3)
```

Форма операндов при этом не меняется: каждая инструкция RiscA — двухадресная, результат
пишется в первый операнд, и верно это одинаково для настоящих инструкций и для виртуальных
(`add t1, b` — `t1 = t1 + b`, `b` не меняется). Третьего операнда в ISA нет, поэтому его нет
и в исходниках A2: новое SSA-значение делают `mov`-копии, а лишние копии аллокатор убирает
коалесценцией (шаг 3 в 7.6), так что правый вариант длиннее только в исходнике, а не в образе.

Исчезает всё, что в левом варианте человек (или `rcc`) обязан вычислять сам: выбор
скретч-регистра, обязанность вернуть значение в `r0`, восстановление callee-saved и самого
кадра на каждом выходе. `ret` из исходника не исчезает — он становится выходом: `ret x`
кладёт `x` в `r0` и уходит к одному на область эпилогу (7.3), а кадр, сейвы и `JMP R14`
в нём генерирует `rasm`. Если у функции есть локалы и вызовы, к тому же списку добавляются
кадр (`SUB R15, …`), сохранение callee-saved регистров и раскладка аргументов `call` —
их тоже генерирует `rasm`.

Принцип приёмки унаследован от A1: **если в исходном коде только физические регистры
`r0..r15`, поведение ассемблера не меняется вовсе** — все новые механизмы включаются
только при появлении имён и новых директив; образцы `samples/` остаются побайтово
идентичны.

### 7.1. О чём речь: словарь вехи

| Термин | Что это | Раздел |
|---|---|---|
| **имя** (виртуальный регистр, переменная) | идентификатор в позиции регистра: `mov t1, a`. Какой это физический регистр — решает аллокатор | 7.6 |
| **слот кадра** | именованное хранилище в кадре: `stw [buf+0], t`. Его адрес `R15 + смещение` считает `rasm` | 7.3 |
| **параметр** | имя из списка `.func f(a, b)`; привязано к `r0..r5` по позиции | 7.3 |
| **область** | диапазон строк от `.func` до `.end` (или до следующего `.func` / конца файла). Только внутри неё действуют имена, кадр и регаллок | 7.2 |
| **именованная область** | область, в которой встретилось хотя бы одно имя. Только в ней и включаются механизмы A2 | 7.2 |
| **интервал жизни** | диапазон инструкций, в котором значение имени нужно | 7.6 |
| **закреплённое использование** | физический регистр, написанный автором внутри именованной области; аллокатор обязан его учесть | 7.7 |
| **спилл** | значение имени уходит в слот кадра, потому что регистров не хватило | 7.6 |
| **выход** | строка `ret x` (или `ret`) в теле: точка, где функция отдаёт значение. Их может быть несколько; эпилог на область один | 7.3 |
| **скретч ассемблера** | физический регистр (`r7`, при раскладке аргументов ещё `r6`), который `rasm` одалживает себе на время разворота псевдокоманды. К именам отношения не имеет | 7.5 |

Последние две строки путать опаснее всего: «временная переменная» (`t1`, пришла из IL) и
«временный регистр» (`r7`, его портит ассемблер) — разные сущности с разной областью
видимости. Про первые — 7.2, про вторые — 7.5.

### 7.2. Область видимости имён — главное новое правило

Пока имена не разложены по одному словарю на область, остальные механики (кадр, регаллок,
карта символов) не имеют смысла: `add t1, b` в `main` и `add t1, b` в `helper` — это
две разные переменные, и путать их нельзя.

**Границы области.** Область начинается строкой `.func` и кончается `.end` — либо,
если `.end` не написан, следующим `.func` или концом файла. Это ровно та же граница,
по которой A1 строит пул констант (6.3: «ближайшая `.func` выше строки, иначе — весь
файл»); нового понятия не появляется, просто у области, кроме пула, появляется ещё и
словарь имён.

**Что и где видно.** Словарь области един: имена параметров, имена в позициях регистров и
имена в позициях памяти (слоты) — всё из одного словаря. Объявления не нужны: имя
рождается своим первым появлением в любой позиции, а параметры объявляет список `.func`.
Словарь живёт строго внутри области:

- вне области имя невидимо, поэтому код вне `.func` (crt0, библиотеки вроде
  `samples/lib/uart.rasm`) остаётся физическим — именам там неоткуда взяться, и механизмы
  A2 молчат (принцип приёмки);
- имена никуда не импортируются и ниоткуда не видны: линковки нет (раздел 1), глобальные
  переменные — это метки плюс `dw`, а не имена;
- одно имя в двух областях — две независимые переменные; конфликт возможен только внутри
  одной области.

**Имя — это не метка.** Метки остаются глобальными и плоскими, как сегодня
(`Assembler.labelMap`), и имена в них не попадают ни при каких условиях; метка никогда не
становится переменной. Полезное следствие: **позиции токенов не пересекаются, и новый
токен не нужен**. Имя занимает только позицию регистра, метка — только позицию ссылки,
поэтому `beqz t1, done` читается однозначно (`t1` — имя, `done` — метка): у `beqz` первый
операнд регистровый, а второй ссылочный.

**Что запрещено — ошибкой сборки, а не тихим затмением**

| Ситуация | Почему |
|---|---|
| имя совпадает с мнемоникой или с `rN` | эти слова уже зарезервированы словарём токенов; проверка та же, что у `.equ` — `Tokenizer.IsReserved` |
| имя совпадает с `.equ`-константой | константы подставляет `Parser.SubstituteConstants` **до** правил парсинга: вместо имени в токенах окажется `NUMBER`, и строка соберётся, но уже не про переменную |
| одно имя — сразу метка и переменная в одной области (`beqz t1, t1`) | формально позиции разные, но выглядит как опечатка; запрет проще, чем объяснение |
| `r7`, `r14`, `r15` в именованной области | 7.5 и 7.7 |

**Служебные имена к словарю не относятся.** Метки, которые генерирует сам ассемблер
(`@over1` из релаксации веток, 6.4; `@ret1` эпилога области, 7.3; слоты пула
`dw label ;pool`, 6.3), живут в `labelMap`
и регаллок их не видит — столкнуться с ними нельзя по построению.

**Зачем это отладчику (M2).** Карта символов обещает «имя → регистр/слот», и без
диапазона адресов области такая запись бессмысленна: `t1` в `main` и `t1` в `helper` —
разные переменные. Поэтому область — единица измерения и для словаря, и для отладочного
вывода (7.9).

### 7.3. Слоты кадра, пролог и эпилог (~1–2 дня)

Локальные переменные компилятор описывает директивами `alloc`/`alloc4`/`alloc8` (IL), и
каждая из них — это просто «мне нужно слово в кадре». Ассемблер умеет обращаться к кадру
через `R15` с маленьким смещением, а считать это смещение и не забыть про `SUB`/`ADD` —
его работа, не работа кодогена.

```
.func sum(n, acc)       ; n→r0, acc→r1
    mov t1, n           ; t1 — регистровое имя (7.6); копия, потому что
    add t1, acc         ;   add двухадресен: t1 = t1 + acc, acc не трогается
    stw [buf+0], t1     ; buf — имя в позиции памяти => автоматический слот кадра
    ldw t2, [buf+0]
    ret t2              ; mov r0, t2 + переход к эпилогу
.end                    ; эпилог: ADD R15, frame + сейвы назад + JMP R14
```

**Формы директив и возврата**

| Форма | Что меняется |
|---|---|
| `.func name(a, b)` | список параметров — новый синтаксис; параметры становятся первыми именами области и привязываются к `r0..r5` по позиции (это и есть преколоринг, 7.6) |
| `.func name:` | прежняя форма, работает ровно как сегодня: область без имён, механизмы A2 её не трогают |
| `.end` | конец области и её эпилог: `ADD R15, frame`, сейв-экспандер назад, spill-`LDW` назад, `JMP R14`. Эпилог на область один, и он — цель всех `ret` области |
| `ret x` | `mov r0, x` + переход к эпилогу. `x` — имя или физический `rN` (кроме `r7`/`r14`/`r15`); направление `mov` именно такое, потому что первый операнд `mov` — назначение |
| `ret` | только переход к эпилогу — возврат без значения, `r0` не трогается |
| `ret` в области без имён | без изменений: `JMP R14`, как сегодня (принцип приёмки) |

**Слоты.** Каждое имя, встреченное в позиции памяти (`[buf]`, `[buf+3]`), получает слот:
нумерация по первому появлению, размер — слово. Смещение внутри скобок остаётся числовым
и остаётся делом `rcc` — это «байты внутри объекта», их `rcc` считает сам; имя слева от
смещения — это передача всей адресации объекта ассемблеру.

**Слот или указатель — как их различить.** Одна и та же запись `[p+0]` может значить две
вещи: «хранилище `p` лежит в кадре» (адрес = `R15 + k`) и «в значении `p` лежит адрес»
(адрес = содержимое регистра под `p`). Различаются они статически и без новой синтаксики,
по тому же SSA-свойству, на котором держится весь регаллок (7.6):

| Ситуация в области | Итог |
|---|---|
| имя появилось **только** в скобках (`buf` нигде больше не определяется) | **слот**: `rasm` сам превращает `[buf+0]` в `[r15+k]` |
| имя имеет определение-значение (`ldw p, […]`, параметр, результат `add`) | **разыменование**: `rasm` выделяет `p` регистр (или спиллит) и превращает `[p+0]` в `[rN+0]` |

Так `alloc4` из IL превращается в `[r15+k]` ровно как обещает `compiler-architecture.md`
(раздел 4), а доступы по указателю остаются доступами по значению. Для рукописных имён с
несколькими определениями правило консервативное: хоть одно определение — значение. Если
окажется, что различать определения недостаточно, правило уточняется сигилом — но решать
это надо до реализации, а не в процессе.

**Кадр.** `SUB R15, frame` в пролог вставляет `rasm`, где `frame` = все слоты области
(включая те, что появились из спилла, 7.6). Пролог и эпилог симметричны, поэтому пересчёт
`frame` после спилла безопасен: меняется размер, а исходный код нет.

**Сейвы.** Сохраняются и восстанавливаются только те `r8..r13`, которые реально испорчены
в теле — область статична, и ассемблер это видит. Набор сейва = имена, поселённые в
`r8..r13` ∪ физически испорченные в теле `r8..r13`. Если в теле нет ни одного `CALL`,
функция листовая и сейвов нет вовсе.

**Несколько выходов: эпилог на область один**

Функция из C возвращает себя столько раз, сколько написано `return`, и qbe-шный `ret`
стоит в каждом возвращающем блоке — их не сливают в один. Значит и в `rasm` выходов может
быть много, и каждый обязан вернуть своё значение и отработать кадр. Делается это одним
эпилогом на область: выход к нему переходит, а не повторяется.

```
.func max(a, b)                 ; a→r0, b→r1
    mov t1, a
    slt t1, b                   ; t1 = (a < b): у сравнения тоже два адреса, результат
    beqz t1, ge                 ;   пишется в первый операнд, отдельного cmp нет
    ret b                       ; -> mov r0, b + j @ret1
ge:
    ret a                       ; -> mov r0, a + j @ret1 (тот же эпилог)
.end                            ; @ret1: сейвы/spill-LDW, ADD R15, frame, JMP R14
```

| Часть | Кто делает | Почему так |
|---|---|---|
| `mov r0, x` | в точке выхода | значение у каждого выхода своё, поэтому переносить его в `r0` обязан именно выход, а не общий эпилог |
| переход к `@ret1` | в точке выхода | служебная метка эпилога области, тот же класс, что `@over1` из 6.4: имена её не видят (7.2) |
| сейвы, spill-`LDW`, `ADD R15, frame`, `JMP R14` | один раз, в конце области | длина эпилога зависит от кадра, сейвов и спиллов — то есть от результата регаллока, а число выходов ничем не ограничено; дублировать эпилог на каждый выход — линейный рост образа |

Порядок и без того правильный: `mov r0, x` выполняется **до** перехода, поэтому результат
переживает и восстановление спиллов, и восстановление `r8..r13` — даже когда `x` жил в
`r8..r13` или в слоте спилла. Отсюда единственное новое правило для аллокатора: **`r0`
исключается из целей восстановления в эпилоге** (сейв-экспандер и spill-`LDW` не должны
писать в `r0`), иначе общий эпилог затрёт возвращаемое значение.

Переход — это обычная `j @ret1` из 6.1, и она релаксируется как все: ближе ±1024 инструкций
это один halfword (`JR`), дальше — пул плюс `r7`, который в именованной области именам
запрещён (7.5), так что релаксация этих переходов безопасна так же, как релаксация веток.
В листовой области без сейвов и спиллов эпилог — это ровно `JMP R14`, поэтому лишний выход
стоит один halfword, а не копию эпилога.

Два следствия — для кодогена и для раскладки:

- телу не нужно иметь единственный выход: `rcc` эмитит `ret v` ровно там, где в IL стоит
  `ret %v` (а голый `ret` — там, где его нет), и ничего не дублирует. Падание потока
  выходов вниз, в эпилог, тоже законно — хвост тела может и не писать `ret`;
- последний `JMP R14` в эпилоге гарантирует, что в пул констант области (он строится после
  эпилога, 6.3) никто не провалится. Тот же порядок касается области без `.end`: эпилог
  вставляется в конец области (перед следующим `.func`), то есть между телом и пулом, а не
  после пула;

**Что запрещено внутри области**

| Запрет | Причина |
|---|---|
| ручная правка `R15` (`sub r15, 4`, `stw [r15+0], r1`) и `push`/`pop` | кадр принадлежит прологу; вне именованной области кадра нет, там `R15` свободен как прежде, а `push`/`pop` — обычный способ им пользоваться (6.1) |
| `r14` | его ставит `CALL`, это адрес возврата |
| `.end` в середине области, после которого код продолжается | это конец области: имена после него относятся к следующей области (7.2) |

`ret` в теле больше не запрещён — он и есть штатный выход (таблица форм выше). Сырые
`jmp rN`/`jr imm`/`jmp label` остаются физическими escape-люками (7.7), и переход по метке
из другой области означает «эпилог пропущен»: кадр и сейвы не восстановлены — это забота
автора, ровно как в физическом режиме, где кадра нет вовсе.

**Оговорка про адресацию.** Смещение в памяти кодируется `Imm3` (3 бита; для слова шаг 4),
то есть базой обязан быть регистр, а смещением — число 0..28 для слов и 0..7 для байтов
(правила `ParseLD`/`ParseST` требуют ровно `[REG + NUMBER]`). Отсюда два вывода, и оба
про `rcc`, а не про человека:

- писать надо `stw [buf+0], t`, а не `mov [buf], t`: у `mov` в RiscA операндов в памяти не
  бывает вовсе (пример выше это учитывает);
- фрейм больше 28 байт одним смещением от `R15` не покрывается. Это уже решено в
  `compiler-architecture.md` (раздел 4: «фрейм ≤ 28 байт; иначе база `r15+K` в начале
  функции»): при большом кадре `rcc` сам заводит имя-базу и обращается `[base+0]`, а
  `rasm` обязан лишь разместить эту базу и не ломать пролог. Ограничение не отменяется и
  тем, что база теперь именованная.
- выражений в скобках по-прежнему нет: `[buf+label]` недопустимо (раздел 1), смещение —
  только число.

**Заметка для реализатора.** `.end` в коде ещё нет нигде: препроцессор
распознаёт только `.equ`/`.include` (полные грамматики в `directiveRules`), а на любую
другую строку с точкой бросает одно сообщение «preprocessor: '<токен>' is not accepted
here» с файлом, строкой и токеном (правило-репортнер над `EQU`/`INCLUDE`/`DOTNAME` в
`directiveRules` — оно стоит после полных грамматик, поэтому известные директивы до него
и не печатаются). Имена `ret x`/`ret`
тоже: у парсера есть единственное правило для
`ret` — `[TK.RET, TK.EOL]` (`ParseRet`), оно жёстко ставит `JMP R14` и не принимает
операндов; нужна новая пара правил (регистровая позиция + пустой выход) и новый
`FixupKind`-подобный переход на метку эпилога — каркас готов: `FixupKind.Jr` и `GetPool`
(6.3) уже умеют «перейти к метке, которой ещё нет».
Директиву `.func name:` теперь разбирает сам парсер: правило `ParseFuncDirective`
снимает токен `TK.FUNC` и помечает строку (`ParsedInstruction.IsFunc`), а ассемблер вставляет
выравнивающий `NOP` перед входом (в первом проходе и в `AlignFuncs`). Для формы
`.func name(a, b)` то же правило нужно дополнить списком параметров (токены `(`, `)`, `,`
в `TK` уже есть); для `.end` аргумент и не нужен — `ret x` несёт имя
в собственной строке.
Отдельно: `.end` — это директива (строка начинается с точки), а метка `end:` — обычная
метка без точки, и препроцессор такие строки не рассматривает вовсе; конфликта у нового
имени с существующим синтаксисом нет.

### 7.4. `call f(a, b)` — вызов по имени со списком аргументов (~полдня, после фикса ABI)

Аргументы должны лежать в `r0..r5` в момент `call`, и в месте вызова они там уже лежат —
если их туда положил тот, кто пишет вызов. Перекладывать их между регистрами, не потеряв
значения (циклы перестановок), — скучная и легко ошибочная задача; её решает `rasm` один
раз, и `rcc` о ней не узнает никогда.

| Форма вызова | Что генерирует `rasm` |
|---|---|
| `call f(a, b)` | перестановка аргументов в `r0..r5` (через свободные `r6`/`r7`, 7.5) + `call f` |
| `call f(a, b, c, d, e, f, g, h)` | то же для первых шести; остальные — на стек по ABI: `SUB R15, 4n`, слова `[R15+0]..[R15+4n-4]` слева направо, вызов, `ADD R15, 4n` после возврата (callee видит их над своим кадром) |
| `call rN` | как сегодня, без изменений: непрямой вызов стековых аргументов не получает — sugar только для статически известного имени |

Поскольку обе стороны (укладка у caller и чтение у callee) генерирует `rasm`, расхождения
«`rcc` сделал одно, `rasm` другое» не остаётся: правило ABI из `instruction-set.md`
(«Stack arguments and frames») живёт в одном месте. В нашем pure-`w` подмножестве
аргумент всегда ровно одно слово, поэтому правил по типам нет.


### 7.5. Область видимости скретч-регистров ассемблера

В вехе A1 появилось новое явление, которого до неё не было: ассемблер **одалживает себе
физический регистр** на время разворота. Это не «временная переменная программиста» — у
него совсем другая область видимости, и путаница между ними стоит дороже всего остального.

**Кто и что одалживает.**

| Разворот | Регистр | Что происходит |
|---|---|---|
| `j label` вне ±1024 (6.4) | `r7` по умолчанию, в `j label, rN` — `rN` | `LDI rN, [@pool]` + `JMP rN`; форма `JR` ничего не портит |
| `call label` вне ±1024 слов (6.4) | всегда `r7` | `la r7, label` + `CALL r7` |
| `la label` (6.1) | никто | ни пул, ни инлайн-мини-пул ничего не портят — за это `la` и выбрана вместо отката к `li` |
| ветка вне ±128 (6.4) | никто | инверсия + `j`; скрытая метка `@over<n>`, регистра нет |
| `ret x` вне ±1024 от эпилога (7.3) | `r7` | тот же дальний `j @retN`: пул + `LDI r7` + `JMP r7` |
| раскладка `call f(a, b)` (7.4) | `r6` и `r7` | промежуточные значения перестановки циклов |

**Область видимости одалживаемого регистра — окно разворота.** Значение в `r7` живо ровно
между первой и последней сгенерированной строкой разворота (`LDI r7, …` → `JMP r7`), и
автор кода не может его ни увидеть, ни использовать: разворот вставляется внутрь его
строки, а не рядом с ней. Всё, что было в `r7` до разворота, после разворота уничтожено,
и наоборот — читать `r7` сразу после разворота нельзя ни в каком режиме. Второй важный
факт: развороты появляются **в произвольных местах** программы (ветка, вызов, `la`,
дальний `j`), и решение о них принимается в петле релаксации, то есть позже, чем
распределяются регистры. Отсюда единственная безопасная формулировка правила: не
«не трогай `r7` возле вызовов», а «`r7` не принадлежит автору нигде».

**Как это разводится с регаллоком.** В именованной области `r7` просто **вырезан из пула
имён** и запрещён как физический операнд (ошибка сборки, 7.2). Тогда к началу петли
релаксации в `r7` не может жить ничего, и разворот, появившийся на любом шаге релаксации,
гарантированно никого не портит — проверить это позже нечем, поэтому запрещено заранее.
`r6` в пул имён попадает: в точке вызова перестановка аргументов забирает его на своё окно,
но имена, живущие через `call`, в `r6` не селятся вовсе (они в `r8..r13`, 7.6), так что
окно скретча и интервал имени пересечься не могут.

**Физический режим (область без имён) не меняется.** Там по-прежнему `r6`/`r7` — общий
свободный scratch ABI (`doc/README.md`, таблица ABI; `samples/lib/uart.rasm` уже живёт на
`r7`), и человек волен использовать `r7` как обычный регистр, помня про правила A1:
безопасно это только в тех строках, разворот которых ничего не портит (`JR`-форма `j`,
`la`, дальняя ветка), а формы через регистр (`j` через пул, дальний `call`) `r7` портят.
Именно двусмысленность «можно или нельзя в этой строке» — причина, по которой в
именованной области `r7` вырезан целиком.

**Явный выбор скретча.** `j label, r3` — и есть способ попросить другой регистр, и в
именованной области это закреплённое использование (7.7): если в этой строке в `r3` живёт
интервал, аллокатор переложит его в другой регистр или спиллит. Директива вида
`.set scratch, rN` для глобальной смены скретча остаётся в отложенных планах (раздел 8)
и относится к физическому режиму — в именованном она не нужна, потому что пул имён от
скретча изолирован.

### 7.6. Регаллок: как он устроен (~3–5 дней)

Суть в трёх действиях — посчитать, кому сколько регистров нужно; раздать; переписать код.
Ниже шесть шагов: первые три готовят данные, четвёртый раздаёт, последние два учитывают
вызовы. Раздача детерминирована: одинаковый вход даёт одинаковый образ, это важно и для
побайтовой приёмки, и для воспроизводимых багов.

**1. Интервалы.** У каждого имени области есть интервал жизни — диапазон инструкций, где
значение нужно. `rcc` пишет в SSA (у временной переменной ровно одно определение), поэтому
интервал один: от определения до последнего использования, и ливность считать не нужно.
Рукописные имена могут определяться несколько раз — тогда интервал консервативный: от
первого определения до последнего использования (неточно, но никогда не ошибётся в
сторону сохранности). Интервалы параметров начинаются с начала области.

**2. Преколоринг — то, что уже стоит на своём месте.** Параметры закреплены за `r0..r5` по
позиции в списке `.func` и не двигаются (переименовать параметр — значит написать `mov`).
Физические регистры, написанные автором внутри области (закреплённые использования, 7.7),
— это короткие закреплённые интервалы: аллокатор не выдаст этот регистр имени, живому в
этой точке.

**3. Коалесценция — склейка копий.** Перед раздачей пары `mov A, B` (это qbe-шные `copy` и
те копии, которыми `rcc` снимает `phi` в концах предшественников) склеиваются: если
интервалы не пересекаются и их классы совместимы (имя, живущее через `call`, нельзя
переселить в caller-saved), они становятся одним интервалом. `phi`-копии становятся
бесплатными — это главная причина, почему `rcc` может снимать `phi` наивными `mov`.

**4. Linear-scan — сама раздача.** Интервалы сортируются по началу (при равенстве — по
номеру строки, чтобы результат был полностью определённым) и раздаются из пула регистров
(таблица 7.7) с активным списком. Регистрам может не хватить — тогда жертва: активный
интервал с самым дальним концом уходит в спилл (`STW` сразу после определения, `LDW`
перед использованием), его слот добавляется в кадр (7.3), размер пролога пересчитывается.
Ситуации «регистров не хватает, сборка падает» не существует: при переполнении всегда
спилл.

**5. Места вызова и точки выхода.** Интервал, живой через `call`, обязан занять `r8..r13`
(callee-saved), иначе он обязан пережить вызов через спилл (`STW` перед вызовом, `LDW`
после). Если свободных `r8..r13` нет, выбирается спилл, а не подмена caller-saved: занять
callee-saved значит добавить сейв в пролог, что дороже для коротко живущего значения.
Точки выхода (`ret x`) — то же самое, только вместо `call` переход к эпилогу: `x` обязан
быть жив в этой строке (он её единственный операнд-чтение), а `mov r0, x` до перехода
значит, что ни сейв-экспандер, ни spill-`LDW` эпилога не должны писать в `r0` — `r0`
исключается из целей восстановления (7.3).

**6. Переписывание.** Операнды заменяются физическими регистрами, вставляются
spill-`LDW`/`STW`, разворачиваются `call f(a, b)` из 7.4 (перестановка аргументов через
`r6`/`r7` — в точках вызова эти два регистра свободны по построению, 7.5) и `ret x` в
`mov r0, x` + `j @ret1` из 7.3. Здесь же становится известен набор сейва пролога:
физически испорченные в теле `r8..r13` ∪ имена, поселённые в `r8..r13`; тот же набор
определяет и содержимое эпилога.

**Где этот проход в конвейере.** Между парсером и петлёй релаксации (Pass B+C, раздел 3):
регаллок разворачивает имена в физические инструкции, длины кода меняются — но пулы и
релаксация только удлиняют код и монотонны, поэтому новое удлинение их не ломает.
Обратный порядок (регаллок после релаксации) невозможен: развороты появляются в произвольных
точках и портят `r7` (7.5), а после раздачи регистров проверить это уже нечем.

### 7.7. Кому какой регистр можно

| Регистр | Виртуальным именам | Почему |
|---|---|---|
| `r0..r5` | параметры — всегда; остальные имена — только если интервал не живёт через `call` | caller-saved; после смерти параметра регистр освобождается и переходит в общий пул |
| `r6` | то же, что `r0..r5` | тот же класс; в точках вызовов занят перестановкой аргументов (7.5), поэтому живущие через `call` имена в него не селятся — конфликта нет |
| `r7` | **никогда** (ошибка сборки и как имя, и как физический операнд) | скретч разворотов A1 и раскладки аргументов; развороты возникают в петле релаксации, после регаллока |
| `r8..r13` | только интервалам, живущим через `call` | callee-saved, покрываются сейвом пролога |
| `r14`, `r15` | **никогда** | адрес возврата и кадр |

**Физические регистры внутри именованной области** — можно, но как закреплённые
использования, и `rcc` их не эмитит вовсе (это escape-люки для рукописного кода):

| Упоминание | Поведение |
|---|---|
| `add r3, x` | закреплённое использование: аллокатор учтёт `r3` занятым в этой точке, а его порча попадёт в набор сейва пролога (`x` — имя, `r3 = r3 + x`) |
| `j label, rN`, будущий `call rN` | `rN` физический; если в этой строке в `rN` попадает живой интервал, аллокатор перекладывает его в другой регистр или спиллит (для single-def проверка тривиальна) |
| результат функции в `r0` | в исходнике не пишется вовсе: выход `ret x` сам положит `x` в `r0` (7.3) |
| `ret x` | `x` — имя (7.3); если в этой строке в `r0` живёт другой интервал, аллокатор перекладывает его в другой регистр или спиллит: `r0` в точке выхода занят значением выхода |
| `ret rN` | `rN` физический, и он же цель `mov r0, rN`; `r7`/`r14`/`r15` здесь запрещены (7.2). `ret` без операнда — выход без значения |
| `r7`, `r14`, `r15` | ошибка сборки (7.2, 7.5) |

Смешивание имён и физических регистров в одной области не запрещено: каждое физическое
упоминание — закреплённое использование, а порча `r8..r13` увеличивает набор сейва
пролога (7.3). Отдельное ограничение добавляет эпилог: ни сейв-экспандер, ни spill-`LDW`
эпилога не пишут в `r0`, потому что к моменту восстановления он уже держит значение выхода
(7.3) — то есть `r0` нельзя использовать и как цель восстановления, и как регистр спилла,
интервал которого жив через точку `ret`.

### 7.8. Что сознательно НЕ добавляем

- `.macro`-производство — ползучий компилятор внутри ассемблера;
- выражения над метками и арифметика в списках аргументов (`call f(a+1, b)` — `rcc`
  эмитит `add` отдельной строкой);
- `cmp`/флаги — это правка ISA (`doc/RiscA.MD`), не ассемблера;
- макросы `sextb/sextw` — без арифметического сдвига и `AND imm` это 3–5 инструкций
  с веткой; знакомое расширение — забота `rcc` (например `ldb` из 0..255 в знаковое —
  `SUB` с переносом, но у `SUB` imm ≤ 127, так что и дешёвый вариант не универсален);
- из мелочи полезна только `.zero n` (zero-fill массивы в qbe-шных `data`) — дёшево,
  входит в 7.3.

### 7.9. Отладочные последствия

Регаллок перестаёт быть тривиально-корректным компонентом, поэтому лист обязателен:
`-vi`/листинг печатают карту имя→регистр/слот и развёрнутые пролог/эпилог; карта
символов `-s` (M2-отладчик) с именами становится заметно ценнее. Чтобы карта была
полезной, каждая её запись обязана нести диапазон адресов области (7.2): имя без области
видимости — это не символ, а два разных символа в одном файле.

### 7.10. Критерий приёмки

- все прежние тесты зелёны; `samples/` побайтово идентичны (в них нет имён и `.end`);
- golden-тесты M3.0 не меняются;
- новые тесты Core.Tests:
  - **область видимости имён**: одно имя в двух `.func` — разные переменные; имя вне
    области неопределено; имя не попадает в `labelMap` и не конфликтует с меткой;
    коллизия имени с мнемоникой/регистром/`.equ`-константой — ошибка сборки;
    `beqz t1, done` разбирается без нового токена (имя в регистровой позиции, метка в
    ссылочной); `.end` не конфликтует с меткой `end:` (директива отличается точкой);
  - **скретч**: `j` через пул и дальний `call` внутри именованной области не портят ни
    одного имени (разворот появляется после раздачи регистров); `r7`/`r14`/`r15` и ручная
    правка `R15` в именованной области — ошибка сборки; в области без имён `r7` по-прежнему
    обычный scratch и ничего не меняется;
  - пролог/эпилог: leaf / non-leaf / частичные сейвы, слоты кадра
    (включая слоты спилла);
  - **выходы**: `ret x` разворачивается в `mov r0, x` + переход к эпилогу; несколько `ret`
    в одной области дают один эпилог и по переходу на каждый; `ret` без значения не трогает
    `r0`; значение `ret x`, жившее в `r8..r13` или в спилле, доходит до вызывающего
    (эпилог не пишет в `r0`); дальний переход к эпилогу релаксируется через пул;
    в области без имён `ret` остаётся `JMP R14`;
  - раскладка аргументов: циклы перестановок, стековые аргументы;
  - регаллок: single-def ливность, спилл, коалесценция `phi`-копий, закреплённые
    физические упоминания, `j label, rN` с живым интервалом в `rN`;
    детерминированность (две сборки одного источника — побайтово равны);
- исполнительные тесты Machine.Tests: функция с параметрами и локальными слотами,
  вызов с 7+ аргументами, вызов через коалесцированные копии, рекурсивная функция
  (сейв `r8..r13` и кадр), функция с двумя `ret` по разным веткам (обе ветки возвращают
  своё значение и получают восстановленные `r8..r13` и `R15`).

## 8. Остальное на потом (после A2)

- `-a <addr>` — адрес загрузки образа (снимет оговорку «образ всегда с 0»); релокация при
  этом опирается на набор `DataAddr`-фиксипов (все `dw label`): в пулах и инлайн-мини-пулах
  лежат абсолютные адреса, и список их слов — это таблица, которую перезаписывает загрузчик;
- `-s <file>` — карта символов для отладчика M2 (формат уже описан в `emulator-architecture.md`, раздел 7);
- выражения с метками в данных (`dw label + 4`) — добавочный `Fixup` со смещением;
- при необходимости — директива выбора временного регистра для релаксаций
  (например `.set scratch, r7`) вместо правки исходников под конфликт.
