# Архитектура ассемблера `rasm`

Документ описывает текущую реализацию ассемблера (`src/RiscA.Core/Asm` + CLI
`src/RiscA.Assembler`) и детальный план вехи **A1** — расширений, без которых невозможен
компилятор C (см. `doc/compiler-architecture.md`, раздел 5). Ссылки: спецификация ISA —
`doc/RiscA.MD`; подробный справочник кодировок с примерами — `doc/instruction-set.md`;
эмулятор и формат симовлов — `doc/emulator-architecture.md`.

## 1. Назначение и границы

`rasm` принимает **один** исходный файл `.rasm` (подключаемые фрагменты — через `.include`)
и выдаёт плоский бинарный образ: последовательность 16-битных слов, начинающаяся с адреса 0.

Что осознанно **не** делает (границы модели):

- нет объектных файлов и линкера — вся программа (код, данные, библиотеки) собирается за
  один проход из одного дерева исходников. Компилятор C следует той же модели: `rcc`
  выдаёт один `.rasm` на всю программу с «вшитой» libc (`compiler-architecture.md`, раздел 1);
- нет директивы адреса (`-a <addr>`): образ всегда стартует с 0; все переходы
  относительные, поэтому образ переезжает на `0x0001_0000` (точка сброса эмулятора) без
  пересборки, лишь бы сохранялось выравнивание;
- нет макросов и условной сборки — до тех пор, пока их не потребует компилятор;
- выражения только над числами, не над метками (`dw label + 4` — нельзя, `dw label` — да).

## 2. Модули и данные

| Файл | Содержимое |
|---|---|
| `Asm/Preprocessor.cs` | `Preprocessor` — склейка `.include`, сбор `.equ`-констант |
| `Asm/Token.cs` | `TK` (виды токенов), `Token`, `Tokenizer.tokenizeLine`, `IsReserved` |
| `Asm/Parser.cs` | `ParsedInstruction`, `Parser` — набор правил и обработчиков |
| `Asm/Assembler.cs` | `SrcLine`, `Assembler` — адресация, метки, разрешение ссылок |
| `ISA/Instruction.cs` | `Instruction` (readonly struct над `ushort`), enum'ы полей, `CheckImmLimits`, `SetImm`, `CalcRef`, `ToString` |
| `Verbose.cs` | флаги `-vp` / `-vi` |
| `RiscA.Assembler/Program.cs` | CLI: `-i` вход, `-o` бинарник, `-l` листинг, `-v[-vp -vi]`, `-V`; печать листинга |

Ключевые структуры:

- **`Token`** — `(TK тип, строка, позиция, intValue, strValue)`. Токенизатор регистронезависим
  для мнемоник и регистров (`r0..r15` несут номер в `intValue`); числа: десятичные, `0x`, `0b`;
  строки — только в одинарных кавычках (`STRING`); комментарий `;` съедает остаток строки;
  в конце дописывается `EOL`. `IsReserved` — проверка, что слово не может быть меткой/константой
  (это мнемоника или регистр).
- **`SrcLine`** — строка исходника + номер строки + файл + адрес + `ParsedInstruction`
  (для строк, не генерирующих код, `ParsedInstruction` предзаполнен пустым — так директивы
  препроцессора не парсятся).
- **`ParsedInstruction`** — результат разбора **одной строки**: `List<Instruction>` halfword'ов
  (одна строка может дать несколько: `db 'text'`, `dw label` — два halfword'а, разворот `li` —
  до четырёх), плюс `Label`, **`Fixups: List<Fixup>`** (отложенные ссылки на метки, 6.2),
  `PoolRequests`, `InlineSlot` (строка уже несёт инлайн-мини-пул, 6.1), `IsFunc`, `IsDW`,
  `IsDB`, `IsPool` (служебный слот пула, вставленный ассемблером).
  Инвариант модели: адрес строки + 2×индекс halfword'а = адрес инструкции.
- **`Fixup`** — изменяемый класс отложенной ссылки: слот halfword'а, имя метки, `FixupKind`
  (Branch/Call/Jr/PoolRef/DataAddr), `Target` (слот пула для PoolRef) и `Reg` (регистр
  разворота `j`) — подробности в 6.2.
- **`Instruction`** — immutable struct: набор кортежей `(mask, shift)`, геттеры
  (`OpCode, Rd, Rs, Func1, Func2, Func21, Func22, Func4, Imm3, Imm7, Imm7s, Imm8, Imm8s, Imm9, ImmCallJr`),
  билдеры `with*` (`this`-копии), `CheckImmLimits(imm)` (диапазоны по опкоду; отдельно
  `SHL/SHR: 0..15`, чтобы ассемблер не давал тихого `imm & 0xF`), `SetImm` (универсальная
  запись imm в нужные поля, для CALL/JR — 11-битное splitting по `Imm7|Rd`),
  `CalcRef(addr)` — куда указывает готовая инструкция (BRANCH/LDI: шаг инструкция ×2 байта;
  CALL_IMM: шаг **слово** ×4 от слова инструкции; JR: шаг инструкция).
  `ToString` — человекочитаемая расшифровка для листинга/дизассемблирования.

## 3. Конвейер

```
файл.rasm
  └─ Preprocessor.Process:
       склейка .include (каждый файл один раз, поиск: каталог включаемого → каталог корня → cwd,
       циклы игнорируются)                     .equ-константы собираются вторым проходом
  └─ Pass A (Parser.ParseLine на каждой строке):
       подстановка констант (LITERAL → NUMBER; «констанка как метка» — ошибка)
       движок правил: список (шаблон токенов → обработчик), цикл «найти первое вхождение
       шаблона в стек токенов — схлопнуть»; выражения (−N, скобки, +−*/) схлопаются в NUMBER;
       «метка:» в начале строки уходит в ParsedInstruction.Label;
       псевдокоманды li/la/j разворачиваются обработчиками правил (6.1), ссылки переходов
       на метки — в Fixups без проверки дальности (её делает петля 6.4);
       .func — NOP для 4-байтного выравнивания на границе;
       непустой остаток токенов = ошибка синтаксиса
  └─ Pass B+C (Assembler, цикл до неподвижной точки, не более 10 раундов — 6.4):
       пересчёт адресов всех строк (curAddress += 2 × число halfword'ов, метки в labelMap)
       → разрешение и релаксация всех Fixups: dw label → абсолютный адрес в 2 halfword'а,
       offset в единицах инструкции (ветки, LDI, JR) или слова (CALL_IMM, с проверкой
       4-выравнивания цели), CheckImmLimits, SetImm; недостижимые ссылки — разворот
       (инверсия ветки + JR, LDI+JMP/CALL r7 через пул или инлайн-мини-пул, слоты пулов,
       AlignFuncs); замены только удлиняют код — петля монотонна и сходится
  └─ Program.cs: .bin (raw halfword'ы LE), .lst, листинг -vi с CalcRef-аннотациями
```

Прямые пользовательские правила описаны в `doc/README.md` (раздел «Директивы ассемблера»).

## 5. Ограничения до A1 — почему она была нужна (историческая справка)

1. **`RefLabel` одна на строку.** Псевдокоманда вида `la` разворачивается в две связанные
   записи (LDI + слот пула), а `j label` — в один halfword с отложенной проверкой дальности.
   Одна ссылка не покрывает ни разворот, ни пул.
2. **Нет релаксации.** Дальность ветки ±128 инструкций, CALL ±1024 слова — для кодогена
   компилятора это норма жизни (циклы, большие функции). Сейчас «далеко» = ошибка.
3. **Нет `li`/`la`/`j`.** Бэкенд компилятора вынужден сам эмитить `movi/movl`-цепочки и
   вручную расставлять пулы — знания про кодировки утекают из бэкенда в код, чего быть не
   должно (см. «зачем A1» в `compiler-architecture.md`, раздел 5).
4. **Проход разрешения ссылок единственный.** Как только разворот меняет длину кода,
   адреса съезжают — нужен цикл до неподвижной точки.

## 6. Веха A1 — план и реализация (детально)

Раздел описывает A1 так, как она реализована в `src/RiscA.Core/Asm/` (`Fixup.cs`,
`Parser.cs`, `Assembler.cs`); расхождения плана с кодом исправлены по факту кода.

Общий принцип: **все знания о кодировках прячутся в `rasm`**; бэкенд `rcc` пишет наивный код
с псевдокомандами, ассемблер сам разворачивает, раскладывает по пулам и релаксует.

### 6.1. Псевдокоманды

Псевдокоманды **не имеют своей кодировки**: парсер разворачивает строку в 1…4 настоящих
инструкции. Смысл — чтобы и кодоген (`rcc`), и человек писали код, не зная про кодировки:
ширину констант, цепочки `MOVI`/`MOVL`, расположение пулов, дальность переходов. Новые
токены `TK.LI/LA/J` добавляются в `Tokenizer` (в словарь мнемоник; `IsReserved` подхватит
их автоматически), разворот — обработчиками в `Parser`: они добавляют несколько halfword'ов
в `ParsedInstruction.Instructions` и записи в `Fixups`.

#### `li Rd, c` — загрузка произвольной константы

Аппаратной инструкции «загрузить 32-битное число в регистр» в RiscA нет: есть только
`MOVI Rd, imm` (записывает 0..255) и `MOVL Rd, imm` (дописывает байт: `Rd = (Rd<<8)|imm`).
`li` собирает из них минимальную цепочку: число берётся как 32-битный паттерн, старшие
нулевые байты пропускаются, первый ненулевой байт грузит `MOVI`, остальные — `MOVL`
(у самого `MOVI` мнемоника та же, что у настоящей инструкции, — разворота в таблицу кодов
не нужно):

```
li r1, 0x12345678   →  movi r1,0x12 ; movl r1,0x34 ; movl r1,0x56 ; movl r1,0x78   (4 инстр.)
li r2, 5            →  movi r2, 5                                                  (1 инстр.)
li r3, 0            →  movi r3, 0          ; особая граница: хотя бы один байт грузим всегда
li r4, -1           →  movi r4,0xFF ; movl r4,0xFF ; movl r4,0xFF ; movl r4,0xFF   (двухкомплементный паттерн)
```

Портит только `Rd`. Конфликт с `ADD Rd,imm` (0..127) и т.п. не возникает — `li` это
всегда ровно `MOVI`+`MOVL`, а не «самая дешёвая последовательность вообще» (короче может
быть через `shl`, но это задача peephole-оптимизации бэкенда, не ассемблера).

#### `la Rd, label` — загрузка адреса метки

Загружает в `Rd` **финальный адрес** метки (функции, строки, таблицы) — тот, который будет
после сборки всего образа. Первый выбор — `LDI Rd, [imm9]` читает 32-битный слот `dw метка`
из пула констант функции, но пул автору расставлять **не надо** — ассемблер сам создаёт
слот (раздел 6.3), сам считает `imm9` и сам пересчитывает его при релаксации. Если слот
пула окажется недостижим (LDI живёт в ±256 инструкциях), `la` не деградирует в `li`, а
переходит на **инлайн-мини-пул**: слот `dw` ставится прямо за загрузкой, а поверх данных
перепрыгивает безусловный переход:

```
la r1, msg          →  ldi r1, +2     ; LDI читает слово через 2 инстр. от себя
                       jr  +3         ; от позиции jr перепрыгнуть 2 halfword'а данных
                       dw  msg        ; финальный адрес метки — всегда «под рукой»
```

(`jr +3` — точное значение считается из положения `jr`, это внутренняя развёртка
ассемблера, вручную такую команду писать не нужно.) `dw` обязан быть word-выровнен — если
строка стоит на нечётном halfword-индексе, ассемблер вставляет `nop` перед `dw`
(см. выравнивающий `NOP` у `.func`), величины `imm` при этом сдвигаются на 1.

Три причины, почему это лучше отката к `li Rd, <адрес>` (цепочка movi/movl та же по цене
3–4 halfword'а):

1. **Достижимость гарантирована**: слот в 2–3 инструкциях от LDI, диапазон больше никогда
   не проверяется и не может «уехать» при релаксации соседей.
2. **Не портится временный регистр** (ср. `j` через регистр, который портит `r7`).
3. Главная, на вырост: **абсолютный адрес остаётся в записи `dw`, а не в кодировке
   инструкции**. `li` зацементирует адрес в цепочке `movi`/`movl` — в готовом образе такую
   ссылку не найти. При инлайн-пуле каждая ссылка на абсолютный адрес — это `DataAddr`
   фиксип, а весь набор `dw` в образе — готовая **таблица релокации**: загрузка образа по
   произвольному адресу (будущее `-a`, A2) сведётся к пересчёту слов из этого списка.

`la Rd, <число>` тоже разрешена — это синоним `li` (единообразие для кодогена: бэкенд может
всегда печатать `la`, а разницу ассемблер спрячет). Портит только `Rd`.

#### `j label [, rN]` — безусловный переход без ограничений по дальности

Переход на метку. Первый выбор ассемблера — `JR` (1 halfword, но ±1024 инструкции); если
не дотягивает — `LDI rN, [@pool]` + `JMP rN` (адрес из пула, дальность не ограничена).
Временный `rN` по умолчанию `r7`; явная форма `j label, r3` использует `r3`. Форма `JR`
ничего не портит, пуловая форма портит `rN`. Это главная псевдокоманда для кодогена:
компилятор печатает `j` и не считает дальность ветки.

#### Почему не добавляем `mv`

В ARM/RISC-V `mv` — это алиас, компенсирующий особенности их `mov` (ограничения операндов,
псевдо-натура). В RiscA `MOV Rd, Rs` — полноценная настоящая инструкция opcode 0 без
ограничений, так что алиас `mv` был бы чистой избыточностью: везде, где хочется `mv`,
пишем `mov` (кодоген `rcc` — тоже). Правило-алиас в парсер не добавляем; если когда-нибудь
понадобится (например, `mv` как «mov с альтернативным разбором» — вряд ли), решение
пересматривается явно.

`db`/`dw` с числами, строками и метками уже есть — данные бэкенд умеет выдавать сегодня.

### 6.2. Фиксипы вместо `RefLabel`

```csharp
enum FixupKind { Branch, Call, Jr, PoolRef, DataAddr }
// Slot — индекс halfword'а внутри ParsedInstruction.Instructions
class Fixup { int Slot; string Label; FixupKind Kind;
              SrcLine? Target;   // слот пула, на который указывает PoolRef (null у
                                 // рукописного ldi — он грузит содержимое по метке)
              int Reg = 7; }     // целевой регистр разворота j label, rN
// ParsedInstruction.Fixups: List<Fixup>;  RefLabel удалён, IsDW/IsDB/IsPool на месте
```

`Fixup` — изменяемый класс, не record: при развороте строки `InsertAndShift` сдвигает
`Slot` всех фиксапов строки, вставленных после точки вставки; релаксация меняет `Kind`
(`Jr → PoolRef`) и `Label` (у инвертированной ветки — на скрытую `@over<n>`).

| Kind | Поле | Единицы | Диапазон | Особенности |
|---|---|---|---|---|
| `Branch` | `Imm8` ветки | инструкции | −128..+127 | при выходе — релаксация 6.3 |
| `Jr` | `Imm7\|Rd` | инструкции | −1024..+1023 | при выходе — `LDI`+`JMP` |
| `Call` | `Imm7\|Rd` | **слова** | −1024..+1023 | цель 4-выровнена (проверка как сейчас); при выходе — `la r7` + `CALL r7` |
| `PoolRef` | `Imm9` LDI | инструкции | −256..+255 | разрешение после расстановки пулов; при выходе — инлайн-мини-пул (6.1) |
| `DataAddr` | 2 halfword'а | абсолют | — | как нынешний `dw label` |

### 6.3. Пулы констант

- Строка, запросившая пул (`la` или релаксированный `j`/`call`), помечает
  `ParsedInstruction.PoolRequests: List<string>`.
- `Assembler.GetPool` на первый запрос вставляет **слот пула** — служебный `SrcLine`
  с `dw`-записью (два halfword'а с `DataAddr`-фиксипом), помеченный `IsPool`, без метки
  (в листинге виден по псевдоисходнику `dw <label> ;pool`). Слот ищется/кэшируется по ключу
  `(область, метка)`: область — ближайшая `.func` выше строки, либо `null` для файла без
  `.func`; вставляется в конец области (перед следующим `.func` или концом файла).
  При нечётной позиции слота перед `dw` вставляется `NOP` — адрес абсолютного слова
  всегда word-выровнен (его читает и `LDI`/`LDW`, и будущий загрузчик-релокатор).
  Если развороты сдвинули `.func` с 4-выравнивания, `AlignFuncs` возвращает `NOP`
  на границу — только добавляет, никогда не убирает.
- `PoolRef` фиксируется на конкретный слот пула (`Fixup.Target`), адрес слота пересчитывается
  на каждой итерации релаксации. Если расстояние больше ±255/256 инструкций — `la` переходит
  на инлайн-мини-пул (6.1). Слот пула при этом **остаётся** (безобидная мёртвая запись,
  следующий `la` на ту же метку в той же области попадёт в тот же слот). Обратно в пул
  решение не откатывается: переключение «пул ⇄ инлайн» туда-сюда ломало бы монотонность
  роста кода и петля могла бы зациклиться.
- Пулы областей не сливаются между собой: локальность пула = предсказуемая близость к коду.

### 6.4. Петля релаксации

**Зачем это нужно.** У всех переходов RiscA фиксированная кодировка и конечная дальность:
`BEQZ/BNEZ` — ±128 инструкций от текущей, `LDI` — ±256, `CALL`/`JR` — ±1024. В коде руки
такое иногда можно облагородить вручную, но для кодогена компилятора «дальние» переходы —
норма: тело цикла в 200 инструкций уже за пределами ветки, а две функции на 300 инструкций
— за пределами CALL. Возникает парадокс: **настоящие расстояния между метками известны
только после всех разворотов, а сами развороты меняют длины и сдвигают адреса**. Релаксация
одной ветки добавляет 1–2 инструкции — и соседняя ветка, которая вчера доставала на +126,
сегодня не дотягивается. Поэтому одиночный проход разрешения ссылок (прежний Pass C)
превращается в цикл до неподвижной точки.

**Как работает цикл.** Инвариант каждой итерации: адреса всех `SrcLine` пересчитаны под
текущий список инструкций, и каждый фиксап либо входит в диапазон своего кодирования, либо
получает замену на более длинную форму. Ключевое свойство: замены **только удлиняют** код
(ветка 1→2+ halfword'а, `call` 1→2+ плюс слот пула, `j` 1→2+ плюс слот пула), а «дальних»
ссылок конечное число — значит процесс монотонно движется к разрешению и обязан
остановиться. Обычно хватает 2–3 итераций; потолок 10 — страховка от зацикливания при баге,
при его превышении — ошибка с перечислением проблемных меток.

```
изменено = true; итераций = 0
пока изменено:
    итераций++; если > 10 — ошибка «relaxation did not converge» + список проблемных меток
    пересчёт адресов всех SrcLine (Pass B-логика заново)
    для каждого фиксапа: вычислить offset/адрес цели
        Branch вне диапазона → заменить строку: <обратная ветка> over; j label; over:
            (beqz→bnez, bnez→beqz; «j» сам тоже может быть релаксирован следующей итерацией)
        Jr вне диапазона     → LDI rN,[пул]; JMP rN
        Call вне диапазона   → la r7, label; CALL r7
        PoolRef вне ±256     → la-строку заменить на инлайн-мини-пул: ldi+jr[+nop]+dw (6.1)
    изменено = (были замены/вставки удалений)
после сходимости — финальный пересчёт и запись фиксипов
```

**Правила с примерами.**

*Дальняя ветка* — инверсия условия плюс безусловный `j` (сам по себе `j` остаётся дешёвым
`JR`, пока цели не дальше ±1024):

```
        beqz r1, end        →   bnez r1, over   ; условие перевёрнуто: «не ветка» — прыгаем вниз
        ...                                       ; над дальним переходом
                                 j   end          ; JR, теперь диапазон ±1024 инстр.
        ...                                  over:
   end:
```

Эта конструкция хрупкая намеренно: вставленные `bnez over` и `j` сами могут оказаться
дальними (соседние развороты сдвинули `over:`) — их подхватит следующая итерация. Именно
поэтому нужен цикл, а не однократная подстановка.

*Дальний `j`/`JR` (за ±1024 инструкции)* — прыжок через регистр с адресом из пула:

```
        j   far              →   ldi r7, [@pool.k]   ; из пула функции — финальный адрес far
                               jmp  r7               ; дальность не ограничена
```

*Дальний `CALL` (за ±1024 слова)* — та же идея, форма `CALL Rd` без ограничений:

```
        call far             →   la  r7, far          ; ленивая форма: ассемблер сам решит,
                               call r7                ; пул это или инлайн-мини-пул
```

*Недостижимый слот пула (`PoolRef` вне ±256 инструкций для `LDI`)* — `la` переводится на
инлайн-мини-пул (`ldi` на слот в 2–3 инструкциях, `jr` поверх данных, `dw label` на месте) —
пример в 6.1. Дальность становится нерелевантной, слово адреса остаётся в `dw` (готовая
таблица релокации для `-a` в будущем).

**Пример сходимости** (цикл, из которого три ветки «на выход» разбросаны по 300
инструкциям кода):

```
итерация 1: дальняя ветка на loop_exit (смещение 260) → инверсия + j (JR±1024 хватает)
итерация 2: адреса сдвинулись на 2 инстр.; вторая ветка (была 126, стала 128) → та же замена
итерация 3: третью ветку сдвинуло на +4 до 131 → замена; j из итерации 1 всё ещё JR — ок
итерация 4: изменений нет — запись фиксипов, готово
```

**Временный регистр `r7`**: по умолчанию псевдо `j` и релаксации `call` портят `r7`. Для
человеческого кода это задокументировано (в `lib/uart.rasm` r7 — уже scratch), компилятор
управляет сам: у ABI аргументы в `r0..r5`, callee-saved `r8..r13`, значит `r7` для бэкенда
всегда свободен; при явном `j label, rN` ответственность на авторе строки.

### 6.5. Листинг и отладка

`-vi`/`-l` показывают каждый halfword разворота с аннотацией `CalcRef`; служебные пуловые
строки печатаются с псевдоисходником `dw <label>  ; pool` — чтобы глазами было видно, где
пул и кому он принадлежит. `-vp` уже сейчас печатает применённые правила — развороты
подхватятся бесплатно.

### 6.6. Тесты (что добавлено в `tests/`)

- `ParserTest` — развороты: `li` (0, 0xFF, 0x100, 0x12345678, −1 → 4 байта, `la Rd,<число>`
  как синоним), `la` (LDI+PoolRequest+PoolRef-фиксап), `j` (JR-фиксап, с rN), числа `j`
  вне диапазона.
- `AssemblerTest` — сквозные: ветка вперёд и назад через 300 инструкций (инверсия + JR +
  скрытая `@over`, адрес цели верный), близкая ветка не трогается, `call` через >1024 слов
  (LDI r7 + инлайн-пул + CALL r7), `j` через >1024 инстр. (LDI rN + JMP rN), `la` на близкую
  метку (imm9 на слот пула), по пулу на каждую `.func`-область, рукописный «далёкий»

- Интеграция с эмулятором (`RunTest`): `Harness.Program(source, ramSize, origin)` собирает

  ветка, дальний `j rN` (инлайн-пул), дальний `call` (LDI+CALL r7, возврат по R14 на `reti`),

- Регресс: все прежние тесты зелёны без правок (кроме четырёх проверок `RefLabel` → `Fixups`);

- Потолок сходимости (10 раундов) — страховочная проверка от бага, специального теста нет:
  reproduce-конфликт, который не сходится за 10 монотонных раундов, вручную не строится.

### 6.7. Критерий приёмки — выполнено

## 7. Веха A2 — переменные, кадры и регаллок (принятый план, пока не реализовано)

Развилка, от которой зависит весь дизайн верха: `rcc` читает QBE IL **до** qbe-шного
регаллока, то есть до него доходят виртуальные temporaries (`%t1, %t2, …`), которых в
16 регистрах RiscA заведомо больше. Регаллок обязан быть где-то — в `rcc` или в `rasm`.
Выбор: **в `rasm`** — та же логика, что в A1 (бэкенд не должен знать ничего о железке:
ни кодировок, ни количества регистров), плюс бонус: IL одноразовая (SSA, у temporaries
одно определение), поэтому живучесть в ассемблере считается тривиально. `rcc` после
этого — почти транспитератор IL, а строчка «базовый регаллок» переезжает из M3.2
в эту веху.

Ключевой принцип приёмки, унаследованный от A1: **если в исходном коде только
физические регистры `r0..r15`, поведение ассемблера не меняется вовсе** — все новые
механизмы включаются только при появлении имён и новых директив; образцы `samples/`
остаются побайтово идентичны.

### 7.1. Называемые слоты, пролог и эпилог (~1–2 дня)

QBE-шные `alloc/alloc4/alloc8` ложатся один в один:

```
.func f(a, b)          ; параметры = первые имена, привязка к r0..r5
    add t, a, b
    mov [x+0], t       ; x — неизвестное имя => автоматический слот кадра
.endfunc               ; .end — конец области: ADD R15, frame + ret
```

- `.func name(a, b)` с параметрами и `.endfunc`/`.end` — новые формы; прежняя
  `.func name:` без списка работает как сегодня (области без имён вообще не трогаются);
- слоты: каждое имя, встреченное в памяти (`[x]`, `[x+3]` — смещения числовые, их
  считает `rcc`), получает слот; нумерация — по первому появлению, размер — слово;
- пролог генерирует ассемблер: `SUB R15, frame`, frame = все слоты + слоты спилла из 7.3;
- эпилог в `.endfunc`: `ADD R15, frame` + `ret`; сохранение/восстановление — только тех
  R8–R13, которые реально испорчены в теле (область статична, ассемблер это видит);
  если в теле нет ни одного `CALL` — листовая функция, сейвов нет; форма
  `.endfunc x` перед `ret` дополнительно кладёт `x` в `r0` — возвращаемое значение
  вообще не требует физического регистра в исходном коде;
- явный `ret` в теле запрещает авто-эпилог (прямые прыжки/джамп-таблицы не ломаются);
- ручная правка `R15` внутри области с именами — ошибка (кадр не должны трогать изнутри).

### 7.2. `call f(a, b)` — вызов по имени со списком аргументов (~полдня, после фикса ABI)

- аргументы раскладываются в `r0..r5` ассемблером: перестановка с циклами перестановок
  через свободные `r6`/`r7` — задача решается один раз здесь, `rcc` о ней не узнает;
- аргументы сверх шести — на стек по зафиксированному правилу ABI (см.
  `instruction-set.md`, ABI: caller кладёт `[R15+0..4n-4]` после `SUB R15,4n`, забирает
  обратно после возврата; callee видит их над кадром) — обе стороны генерирует `rasm`,
  расхождения «`rcc` vs `rasm`» не останется;
- в нашем pure-`w` подмножестве аргумент всегда одно слово — правил для типов нет;
- рукописный `call rN` (непрямой вызов) стековых аргументов не получает — sugar только
  для статически известного имени.

### 7.3. Имена как виртуальные регистры + linear-scan (~3–5 дней)

Неизвестный идентификатор в позициях операндов — виртуальный регистр; те же имена,
что и в 7.1, — единый словарь области. Область считается «именованной», если в ней
встретилось хотя бы одно имя (параметр, слот или операнд); в именованной области
работает регаллок, в остальном — ничего не меняется.

**Как работает аллокатор, по шагам**

1. **Интервалы.** У каждого имени интервал жизни. Single-def (SSA-форма `rcc`
   сохраняется до самого конца) — ровно один интервал от определения до последнего
   использования; для рукописных имён с несколькими определениями определения
   склеиваются в один консервативный интервал (первое определение .. последнее
   использование — менее точно, но корректно). Интервалы параметров начинаются с
   начала области.
2. **Преколоринг.** Параметры закреплены за `r0..r5` по позиции в списке — их
   интервалы не двигаются (переименование параметра — это `mov`). Прямые упоминания
   физических регистров внутри области (правила ниже) — короткие закреплённые
   интервалы: аллокатор не даёт этот регистр имени, живому в этой точке.
3. **Коалесценция.** Перед раздачей склеиваются пары `mov A, B` (qbe-шные `copy` и
   копии, которыми `rcc` снимает `phi` в концах предшественников): если интервалы не
   пересекаются и классы совместимы (имя, живущее через `CALL`, нельзя переселить в
   caller-saved), они становятся одним интервалом — `phi` становится бесплатным.
4. **Linear-scan.** Интервалы сортируются по началу (tie-break по номеру строки —
   полная детерминированность), раздаются из пула (таблица ниже) с активным списком.
   При нехватке жертва — активный интервал с самым дальним концом; он уходит в спилл
   (`STW` после определения, `LDW` перед использованием), слот добавляется в кадр
   (7.1), размер пролога пересчитывается. Ошибки «регистров не хватает» не бывает —
   при переполнении всегда спилл.
5. **Места вызова.** Интервал, живой через `call`, занимает только `r8..r13`, иначе
   спилл через вызов (`STW` перед вызовом, `LDW` после) — при нехватке `r8..r13`
   спилл предпочтительнее: занимать callee-saved ради коротко живущего значения
   дороже (сейв в прологе).
6. **Переписывание.** Операнды заменяются физическими регистрами, вставляются
   spill-`LDW/STW`; здесь же разворачивается `call f(a, b)` из 7.2: раскладка
   аргументов в `r0..r5` перестановкой через `r6`/`r7` — в точках вызова они свободны;
   набор сейва пролога = испорченные физически в теле `r8..r13` ∪ имена,
   поселённые в `r8..r13`.

**Кому какой регистр можно**

| Регистр | Виртуальным именам |
|---|---|
| `r0..r5` | параметры — всегда (преколоринг); прочие имена — только если интервал не живёт через `call` (caller-saved), после смерти параметра регистр освобождается |
| `r6` | то же, что `r0..r5`; на местах вызовов задействован перестановкой аргументов — конфликта нет, живущие через `call` имена в `r6` не селятся |
| `r7` | никогда — зарезервирован под развороты A1 (`la`/`j`/`call`), конфликта с релаксацией не будет |
| `r8..r13` | только интервалам, живущим через `call`; покрываются сейвом пролога |
| `r14`, `r15` | никогда |

**Где регистры напрямую, а где только через имена**

- области **без имён** (старые `.func name:`, код уровня файла без `.func`, crt0,
  библиотеки вроде `samples/lib/uart.rasm`) — чистая физика, поведение A1, все
  механизмы A2 молчат;
- **именованная область** — физический регистр разрешён только как закреплённая
  точка, и то с оговорками:
  - возвращаемое значение: физический `r0` в исходниках не нужен вовсе —
    `.endfunc x` сам положит `x` в `r0` перед `ret`;
  - непрямые переходы `j label, rN` (и будущий `call rN`) — `rN` физический; если в
    этой строке в `rN` попадает живой интервал, аллокатор перекладывает его в другой
    регистр или спиллит (для single-def проверка тривиальна);
  - прочие упоминания (`add r3, x, 1`) формально разрешены как закреплённые
    использования, но `rcc` их не эмитит — это escapes для рукописных случаев;
  - под запретом в именованной области: `r14`/`r15` (кадр и линковка) и `r7`
    (временный регистр разворотов) — ошибка сборки;
- смешивание в одной области не запрещено: каждое физическое упоминание — закреплённое
  использование, а порча `r8..r13` попадает в сейв-набор пролога (7.1).

Проход регаллока — **между парсером и петлёй релаксации** (B+C): имена разворачиваются
в физические инструкции, длины меняются — пулы и релаксация монотонны и это переживут.

Регаллок детерминирован; карта имя→регистр/слот и вставленные spill-`LDW/STW`
печататься будут (см. 7.5).

### 7.4. Что сознательно НЕ добавляем

- `.macro`-производство — ползучий компилятор внутри ассемблера;
- выражения над метками и арифметика в списках аргументов (`call f(a+1, b)` — `rcc`
  эмитит `add` отдельной строкой);
- `cmp`/флаги — это правка ISA (`doc/RiscA.MD`), не ассемблера;
- макросы `sextb/sextw` — без арифметического сдвига и `AND imm` это 3–5 инструкций
  с веткой; знакомое расширение — забота `rcc` (например `ldb` из 0..255 в знаковое —
  `SUB` с переносом, но у `SUB` imm ≤ 127, так что и дешёвый вариант не универсален);
- из мелочи полезна только `.zero n` (zero-fill массивы в qbe-шных `data`) — дёшево,
  входит в 7.1.

### 7.5. Отладочные последствия

Регаллок перестаёт быть тривиально-корректным компонентом, поэтому лист обязателен:
`-vi`/листинг печатают карту имя→регистр/слот и развёрнутые пролог/эпилог; карта
символов `-s` (M2-отладчик) с именами становится заметно ценнее.

### 7.6. Критерий приёмки

- все прежние тесты зелёны; `samples/` побайтово идентичны (в них нет имён и `.endfunc`);
- golden-тесты M3.0 не меняются;
- новые тесты Core.Tests: раскладка аргументов (в т.ч. циклы перестановок и стековые),
  пролог/эпилог (leaf / non-leaf / частичные сейвы, `.endfunc x`), регаллок (single-def
  ливность, спилл, коалесценция `phi`-копий, закреплённые физические упоминания),
  ошибки на `r7`/`r14`/`r15` и ручную правку `R15` в именованной области;
- исполнительные тесты Machine.Tests: функция с параметрами и локальными слотами,
  вызов с 7+ аргументами, вызов через коалесцированные копии.

## 8. Остальное на потом (после A2)

- `-a <addr>` — адрес загрузки образа (снимет оговорку «образ всегда с 0»); релокация при
  этом опирается на набор `DataAddr`-фиксипов (все `dw label`): в пулах и инлайн-мини-пулах
  лежат абсолютные адреса, и список их слов — это таблица, которую перезаписывает загрузчик;
- `-s <file>` — карта символов для отладчика M2 (формат уже описан в `emulator-architecture.md`, раздел 7);
- выражения с метками в данных (`dw label + 4`) — добавочный `Fixup` со смещением;
- при необходимости — директива выбора временного регистра для релаксаций
  (например `.set scratch, r7`) вместо правки исходников под конфликт.
